# Account authentication and policy audit

**Scope:** source review for IMRS-9 Task 5, checked 2026-10-08. This records implemented flows and references to re-check; it is not a legal opinion, provider approval, or live-account test.

## Implemented account flows

- **ChatGPT:** `OpenAIAccountClient` runs browser OAuth with loopback callback, random state and nonce, and S256 PKCE. It exchanges the code, verifies the returned ID token against OpenAI JWKS (RS256 signature, issuer, audience, expiry, nonce, subject, and authorized party), and stores the account session in the credential store. The direct API access and refresh tokens are retained only when `chatgpt.tokens.use.direct` is granted. See `OpenAIAccountClient.makeSignInRequest/completeSignIn/exchangeAndStore` and `OpenAIIDTokenValidator.validate`.
- **Hugging Face:** `OfficialAccountClient` uses loopback authorization-code OAuth with state and S256 PKCE for `openid profile inference-api`. It validates the bearer token's shape, type, expiry, and required scopes, then uses that token to fetch the profile label and stores the access/refresh tokens. It does not decode or validate an ID token; the OAuth response model does not consume one.
- **OpenRouter:** loopback authorization-code OAuth uses state and S256 PKCE, then exchanges the code at OpenRouter's key endpoint for a user-controlled API key. The app stores that key as its account credential; this is not an OAuth bearer/refresh-token session.
- **GitHub Copilot:** GitHub device authorization requests `read:user`, polls for a bearer token, checks the returned scope and fetches the GitHub profile label. On a generation request the app passes that token to a local Copilot runtime process over its JSON-RPC login method. The runtime is discovered from fixed executable candidates; the app does not embed a GitHub client secret.
- **Other providers:** `ProviderKind` distinguishes ChatGPT/OpenAI API, Anthropic, OpenRouter/Hugging Face/Copilot accounts, compatible endpoints, and managed local inference. The remaining remote providers use separately configured API credentials; no consumer subscription OAuth flow for them is implemented here. See `../Sources/ImrseCore/Contracts.swift` and `official-provider-connections.md`.

## Code-backed security boundaries and risks

- ChatGPT ID-token verification is substantive: `OpenAIIDTokenValidator` restricts the algorithm to RS256, selects one matching RSA key from the fetched JWKS, verifies the signature with Security.framework, and checks issuer, audience, expiry (with five seconds of clock tolerance), nonce, subject, and `azp`. On platforms without Security.framework it fails closed. This establishes the code's validation behavior, not that a current live provider response was tested.
- Hugging Face and GitHub access tokens are treated as opaque provider-issued credentials, not locally signature-verified JWTs. Hugging Face validates response fields/scopes and calls its user-info endpoint; GitHub validates bearer/scope fields and calls `api.github.com/user`. The service remains authoritative for whether either token is valid. This is distinct from the ChatGPT ID-token validation above.
- `CopilotProcessRuntime` checks that the selected file is executable, rejects a `.js` path, enforces a minimum runtime-reported version, and launches it with a temporary home, restricted environment, tool-free session settings, and `persist: false`. It does not verify a code signature or hash, nor OS-sandbox the child. The child runs with the app user's OS permissions and receives both the GitHub access token through `session.gitHubAuth.login` and the request prompt. A replaced or compromised executable at a discovered candidate path could therefore read the token or request data; this is a concrete trust-boundary risk, not evidence of an exploit or of a compromised installation.

## Official sources to re-check for the selected account and plan

- **OpenAI / ChatGPT:** [Sign in with ChatGPT for open-source apps](https://developers.openai.com/siwc/token-sharing-open-source), [Terms of Use](https://openai.com/policies/terms-of-use/), and [Usage Policies](https://openai.com/policies/usage-policies/). Check the current account/plan authorization, permitted use of direct plan tokens, and any limits relevant to this app; do not infer ChatGPT-plan permission from API-key terms.
- **Hugging Face:** [OAuth scopes](https://huggingface.co/docs/hub/oauth), [Terms of Service](https://huggingface.co/terms-of-service), [Privacy Policy](https://huggingface.co/privacy), and [Inference Providers pricing and billing](https://huggingface.co/docs/inference-providers/en/pricing). Check the currently granted scopes, account/organization billing, and the selected inference provider's own data terms.
- **GitHub Copilot:** [GitHub Terms of Service, section J](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service), [Terms for Additional Products and Features](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features), [Copilot SDK authentication](https://docs.github.com/en/copilot/how-tos/copilot-sdk/auth/authenticate), [individual policy controls](https://docs.github.com/en/copilot/managing-copilot/managing-copilot-as-an-individual-subscriber/managing-your-copilot-plan/managing-copilot-policies-as-an-individual-subscriber), and [usage-based billing](https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-individuals). Which terms and controls apply depends on whether the account is individual or organization/enterprise-managed. The runtime in this repository uses a custom local process protocol, so SDK guidance is a reference to compare against, not proof that this implementation is the SDK.
- **OpenRouter:** [OAuth PKCE](https://openrouter.ai/docs/guides/overview/auth/oauth), [Terms of Service](https://openrouter.ai/terms), [Privacy Policy](https://openrouter.ai/privacy), and [provider logging/data-retention guidance](https://openrouter.ai/docs/guides/privacy/provider-logging). Review the account's routing/privacy settings and the selected model provider's linked policies as well as OpenRouter's own terms.
- **Other API-key providers:** review the selected service's current API terms, privacy/data-retention rules, model license, and billing rules. Those are separate from the account sign-in flows above.

**Verification limit:** no live provider sign-in, account entitlement, billable inference, runtime execution, or policy/legal determination was performed for this audit. The linked pages are official starting points, not an assertion that a flow is permitted for every account or plan.
